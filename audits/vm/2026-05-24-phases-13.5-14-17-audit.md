# FlameVM Phase 13.5 / 14 / 17-partial audit — 2026-05-24

**Scope**: encrypted `borrow` + cloak `mix` gadget (13.5); batch

## 1. Encrypted `borrow` overload (Phase 13.5)

### What we did

- `dispatch_external` peek-then-dispatch routes `Borrow` to
  `op_borrow_encrypted` when both top-two stack values are
  `Variable`. Cleartext Int253 path stays in `dispatch_common`.
- `op_borrow_encrypted`:
  1. Pops `flv, qty: Variable`.
  2. Commits both to CS (uses `Delegate::commit_variable`).
  3. Range-proves `qty` (64-bit, `spacesuit::BitRange::max()`).
  4. Allocates `neg_qty_var` with witness `-qty_assignment`.
  5. Constrains `qty_var + neg_qty_var == 0`.
  6. Builds `WideToken(AllocatedValue { q: neg_qty_var, f: flv_var, … })`
     and `Token { qty: qty.commitment, flv: flv.commitment }`.
  7. Pushes both (WideToken at bottom, Token on top).

### How zkvm does it

zkvm's `borrow` is structurally identical:
- Pops two Variables.
- Commits both, range-proves qty.
- Allocates `neg_qty_var`, constrains balance.
- Pushes `WideValue` + `Value` pair.

### Divergences

None substantive. Variable / Token names differ; semantics match.

### Risk surface

✅ **L1 (low)**: the `WideToken` is non-portable and non-droppable.
A script that does `borrow` without consuming the `WideToken` via
`mix` / `fee` / `decrypt` will leave it on the stack → finalize
hits `StackNotClean`. This is correct linear-type behavior.

✅ **Tested**: `encrypted_borrow_produces_widetoken_and_token_pair`
hand-drives the VM and inspects the stack post-borrow.

## 2. `mix` (cloak gadget) (Phase 13.5)

### What we did

- `op_mix` pops `n` (outputs), then `m` (inputs); pops `n` output
  Pedersen-commitment String pairs (qty, flv); pops `m` input
  token-shaped values; converts each via `value_to_allocated` to a
  `spacesuit::AllocatedValue`; invokes `spacesuit::cloak(cs, ins,
  outs)`; pushes `n` output `Token`s.
- `value_to_allocated` handles:
  - `WideToken`: unwraps inner `AllocatedValue` via the
    `allocated()` accessor.
  - `Token`: commits both Commitments to CS, builds AllocatedValue.
  - `ClearToken`: promotes to unblinded `Token`, then recurses.
  - Other: `TypeNotToken`.

### How zkvm does it

zkvm's `cloak(m, n)` opcode is identical in shape — same pop order,
same `item_to_wide_value` / `value_to_cloak_value` helpers.

### Divergences

- **Operand ordering**: zkvm pops `(m, n)` as opcode-immediate
  arguments; FlameVM pops them as runtime Int253 values. Different
  encoding mechanism, same semantics.
- **ClearToken support**: FlameVM's `value_to_allocated` promotes
  ClearToken to unblinded Token transparently — zkvm doesn't have
  this case because they have no `ClearValue` on the stack at
  cloak time.

### Risk surface

⚠️ **M1 (medium)**: `spacesuit::cloak` calls `mix.rs::k_mix` which
underflows for `k=0`. Tests confirm `n=0` paths are unreachable
through the cloak gadget (we'd need `n ≥ 1` outputs to balance). A
malicious script with `n=0` would panic the verifier. **Recommend**
a pre-check in `op_mix` that errors if `m == 0 || n == 0`.

✅ **Tested**: `mix_with_single_in_single_out_balances` exercises
the simplest balanced shape (m=1, n=1, same Token in/out).

## 3. Batch-verifier infrastructure (Phase 14)

### What we did

- Added `Delegate::BatchVerifier: musig::BatchVerification` and
  `fn batch_verifier(&mut self) -> &mut Self::BatchVerifier`.
- `Prover<'g>` and `Verifier` both hold
  `musig::BatchVerifier<ThreadRng>`.
- `Verifier::verify` walks `deferred_sigs`:
  - For each `Explicit { vk, message, sig }`: rebuild transcript
    (`flamevm.signrun.v1`, append `b"msg"`, message bytes); call
    `Signature::from_bytes(sig)?.verify_batched(t, vk, &mut
    batch)`.
  - `TxBound` left for Phase 17 (needs TxID).
- After R1CS proof verification succeeds, calls `batch.verify()` →
  `BatchSignatureVerificationFailed` on failure.

### How zkvm does it

zkvm's pattern is identical:
- `Delegate::BatchVerifier` associated type with the same trait
  bound.
- Prover/Verifier hold their own batch verifier.
- At finalize: `signature.verify_multi_batched(transcript,
  signtx_items, &mut batch)` for the aggregated multi-sig, plus
  appends from `unblind` / `issue`'s flv-check.

### Divergences

- **Single-sig vs multi-sig**: zkvm has a single tx-envelope
  signature aggregating all TxBound sigs (musig). FlameVM
  currently has individual `Explicit` sigs from `signrun`; the
  TxBound aggregation lands in Phase 17.
- **`MultiscalarMul` deleted**: zkvm doesn't have such a type;
  FlameVM's spec listed it but no opcode used it. Removed cleanly
  with a TODO note for spec.md (architect ADR required to retire
  the type table row).

### Risk surface

⚠️ **M2 (medium)**: `BatchSignatureVerificationFailed` returned
without distinguishing which signature failed. Phase-17 multi-sig
aggregation will compound this — a single bad TxBound sig fails
the whole batch. Mirrors zkvm's pattern, so acceptable.

⚠️ **M3 (medium)**: prover and verifier batches use independent
RNGs (`rand::thread_rng()`). Batched MSM uses random weights — a
verifier with non-cryptographically-secure RNG would let an
attacker forge proofs. `ThreadRng` is OS-backed (good); but if
this ever runs on a no-std target, RNG choice needs review.

✅ **Tested**: `signrun_explicit_sig_batch_verifies_correctly`
proves a real Schnorr sig over the signrun transcript and asserts
the batch verifies.

## 4. `TxID` + `log` opcode (Phase 17 partial)

### What we did

- `TxID::from_log(txlog) -> TxID` — merkle root over txlog with
  domain `flamevm.txid.v1`.
- `MerkleItem for TxEntry` — per-variant `commit(t)` that absorbs
  type-tagged bytes. Variants: Data, Input, Output (via
  cell.id()), Issue, Retire.
- `op_log` (`0x6f`): `str → ø`, pops a String, pushes
  `TxEntry::Data(bytes)` to txlog.
- `Instruction::Log` variant + `Program::log()` builder.

### How zkvm does it

zkvm's `TxID::from_log` is the exact pattern — `MerkleTree::root`
with a domain string (`ZkVM.txid`). `MerkleItem for TxEntry` does
the same per-variant commit. `op_log` is also at 0x6f.

### Divergences

- **Header included in zkvm**: zkvm's TxEntry has a `Header`
  variant (version, mintime, maxtime). FlameVM doesn't put header
  into the txlog yet — it lives in `VM.header` separately. Phase
  17 full will need to include it for the TxID to bind to the
  full tx context.
- **Output commit**: zkvm absorbs `contract.id()`; we do
  `cell.id()`. Identical mechanism, different type name.
- **No `Fee` variant yet**: zkvm has `TxEntry::Fee(u64)`; FlameVM
  Phase 17 full will add it.

### Risk surface

⚠️ **L2 (low)**: header not yet bound into TxID. A txlog with
identical effects but different `(version, locktime)` would
produce the same TxID. Phase 17 full must add `TxEntry::Header`
or absorb the header into the merkle root prefix.

⚠️ **L3 (low)**: TxID is computed but **not yet bound into the
R1CS transcript**. zkvm does
`prover.cs.transcript().append_message(b"ZkVM.txid", &txid.0)`
before proving; FlameVM Phase 17 full needs the same to bind the
proof to the full effect set. Currently the proof binds only to
the algebraic statement.

✅ **Tested**: `txid_from_log_is_deterministic_and_distinguishes_entries`,
`txid_distinguishes_entry_order`,
`txid_distinguishes_input_from_output_entries`. The merkle root
mechanism is exercised; entry-discrimination via the
domain-tagged commit absorbs is verified.

## 5. Cross-system comparison: confidential-balance + tx-binding

| System | Confidential balance check | Tx-ID binding | Sig batching | Log/event mechanism |
|---|---|---|---|---|
| **FlameVM** | spacesuit::cloak (Mimblewimble lineage) | `TxID::from_log` merkle root (Phase 17 binds to proof) | musig::BatchVerifier | `0x6f log` → TxEntry::Data |
| **zkvm** | spacesuit::cloak (same) | `TxID::from_log` bound to R1CS transcript | musig::BatchVerifier | `0x6f log` |
| **Mimblewimble / Grin** | Pedersen sum check (CT) | n/a (kernel hash) | aggregated Schnorr | n/a |
| **Monero RingCT** | Bulletproofs+ | tx hash | per-input MLSAG | n/a |
| **Zcash Sapling** | Notes + Spend/Output descriptions | shielded tx hash | binding sig | memo field |
| **Solana Confidential SPL** | Pedersen + sigma protocols | tx signature | per-instruction | logs API |
| **Aleo / snarkOS** | Records (zk-snark) | transition root | per-input | events |

### Observations

1. **FlameVM + zkvm sit in the Mimblewimble/Grin lineage** for
   confidential-balance checks (Pedersen commitments + cloak/range
   proofs). The programmability surrounds it (Forth-like stack
   machine) rather than baked-in tx format.
2. **TxID merkle root** is uncommon outside zkvm-lineage —
   Mimblewimble uses kernel-hash, Monero uses tx hash, Zcash uses
   shielded-tx hash. Merkle root is more compact-proof-friendly
   (per-entry SPV).
3. **Batched Schnorr verification** is universal in modern
   confidential-asset systems — musig is the right call.
4. **`log` as a TxEntry** is FlameVM/zkvm-specific. Most other
   systems use event logs separate from the canonical state; for
   FlameVM, log entries are part of the txid and the outer
   verifier sees them — useful for protocol-level data binding.

## 7. Recommendations

1. **Phase 17 full (next priority)**: 
   - Add `TxEntry::Header(TxHeader)` variant; emit at run start.
   - Bind TxID into prover/verifier transcript (zkvm one-liner).
   - Add `op_fee` and `TxEntry::Fee(u64)`.
   - Wire TxBound multi-sig verification via
     `signature.verify_multi_batched(...)`.
   - Expose `txlog` through Prover/Verifier return values.

2. **`op_mix` zero-count guard**: pre-check `m > 0 && n > 0` to
   avoid spacesuit panic. Trivial fix; recommend before any
   external user exposure.

3. **Encrypted `issue`**: needs an ADR. Either:
   - Match zkvm exactly (take Predicate from stack — drops the
     actor-context dependency).
   - Make `issue` internal-only (so actor context is always
     present).
   - Introduce an "issuer" stack pop (explicit cid).

4. **Phase 14 follow-up — DRY BulletproofGens**: lift to a
   thread-local or lazy-static singleton. Each Prover/Verifier
   currently re-allocates ~16 KB.
