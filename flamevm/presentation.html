FlameVM

a stack machine that verifies the Flame blockchain
architecture overview · ◉ 2026

What it is

A Forth-like stack machine
with linear types.

Each transaction instantiates a fresh VM, executes a script, emits a list of effects.

Successful execution = successful transaction verification.

Built-in network rules and user-authored application rules live in the same place: the script.

◉ FlameVM2 · what it is

Two execution contexts

External  ·  Internal

External

User-composed and signed. Verifiable in parallel.

  • Reads & writes Utreexo (UTXO set)
  • Confidential — Bulletproofs
  • Pays a fee atomically
  • Outcome fixed at signing time

Internal

Triggered by a message send. Verified serially.

  • Reads & writes the actor registry
  • No Bulletproofs (no fixed outcome)
  • Gas committed by originating send
  • Outcome depends on live actor state

◉ FlameVM5 · tx → state

Key idea

The whole transaction is a script.

No rigid input / output layout. The script is the transaction.

Bitcoin

Fixed lists: inputs, outputs, witnesses. Each input runs a tiny isolated script.

FlameVM

One script per transaction. input / output / split / merge / send are instructions, executable in any order.

Effects are emitted as the script runs. TxID is the Merkle root over those effects — once signed, they commit atomically.

◉ FlameVM6 · tx is a script

External transaction

A pipeline of instructions

Stack-based: values flow up the stack; opcodes pop & push. No control flow other than run / switch / loop / break.

◉ FlameVM8 · effects

Cells

A UTXO is a cell.

Single-use container of values, locked by a predicate.

In-VM lifecycle

input materializes a cell on the stack.

output seals portable values back into a fresh cell.

Open the cell — payload is released onto the stack, the cell vanishes.

Cells are linear: no copying, no double-spending by construction.

◉ FlameVM9 · cells

Cells in the script

input & output are instructions.

Linearity is enforced by the type system: tokens cannot be duplicated or dropped, so an opened cell must be balanced into outputs (or burned).

◉ FlameVM10 · input / output

Authorization

Cells locked under a Taproot predicate.

On chain: a single 32-byte Point. Hides every alternative spending path.

The unspent script paths stay hidden. An observer sees only the point.

◉ FlameVM11 · taproot

Two paradigms for contracts

Cells  vs  Actors

Cell

Ephemeral private covenant.

  • Compressed (32 bytes on chain)
  • Single-use, single-owner
  • Confidential (Bulletproofs)
  • Built & signed off-chain

payments · vaults · multisig · escrow · HTLCs

Actor

Long-living multi-user app.

  • Uncompressed, addressed by id
  • Persistent state, many callers
  • Public (no Bulletproofs)
  • Concurrent messages serialized by actor

AMM · order books · registries · oracles

External tx writes cells & sends messages. Internal tx mutates actors. Both live in the same VM.

Actor

Two dicts — public & private.

ActorState = Dict {
  0x00 public:  Dict {
    0 recv:     // reserved entrypoint
    1 swap:     // callable by other actors
    2 deposit:
    …
  }
  0x01 private: Dict {
    // helpers, balances, reserves, …
  }
}

Identity

ActorID = hash(initial state)  or 

ActorID = enum { Constructor } — on-the-fly deploy.

Each unique constructor defines a unique actor.

Dispatch

send → key 0 (recv), async, must not return.

call → any public key, sync, may return values.

◉ FlameVM13 · actor

Addresses

Where a payment goes.

Address = enum {
  0 Predicate                          // unlock path for a cell
  1 MessageTarget {
       dst:    ActorID
       method: MethodKey
       args:   Tuple
       gas:    Int253
     }
}

Same address space for cells and messages. A payment is either "to this lock" or "to this actor method".

Each send also carries an anchor — a 256-bit value unique to its originating transaction. Anchors disambiguate otherwise-identical sends and stop replay across blocks.

◉ FlameVM14 · addresses

Data discipline

Every value is owned.

No references, no borrowing, no implicit copies.

copyable

May be duplicated by dup.

Int253, String, Point, certain Dicts.

Non-copyable: tokens, transcripts, MSM — anything bearing scarce value.

portable

May exist in persistent state outside the VM.

All plain types; ClearToken ≥ 0.

Non-portable: WideToken, Variable, Expression, Constraint, Merlin, MSM.

Dicts inherit flags from their contents. One non-portable item poisons the whole dict.

◉ FlameVM15 · linearity

Primitive type

Int253 — a versatile signed scalar.

Canonical Ristretto scalar (< ℓ ≈ 2²⁵²) + explicit sign bit.

One type, many roles

  • Counters, indices, booleans (0/1)
  • Cleartext token quantities
  • Dict keys (total numeric order)
  • Scalars feeding ZK proofs

Compact encoding

0x00..0x0f inline 0..15
0x10/0x11 ±1-byte payload
0x12/0x13 ±2-byte
0x14/0x15 ±8-byte
0x16/0x17 ±16-byte
0x18      full 32-byte

Width classes carve disjoint value ranges — one canonical encoding per value. No negative zero.

◉ FlameVM16 · Int253

Primitive type

String — bytes + reader/writer.

Variable-length byte sequence. Doubles as a streaming builder and a streaming parser.

Builder

  • append — concat two strings
  • writeint, writebits, writezeros
  • bitnot / bitand / bitor / bitxor
  • shiftleft / shiftright

Reader

  • readint, readbits
  • readstr n — take a substring
  • readpoint — pull a 32-byte point
  • Other types decode from a String

Strings carry programs, signatures, hashes, cell encodings, predicate scripts — anything byte-shaped.

◉ FlameVM17 · String

Primitive type

Point — Ristretto255 group element.

Used for

  • Public keys (signatures, MuSig)
  • Pedersen commitments (encrypted values)
  • Taproot predicates (cell locks)

Arithmetic lifts

P + Q→ MSM
k * P→ MSM
-P→ MSM
P * Q→ fail

Stored compressed: 32 bytes. Decompression is lazy — an invalid encoding fails only when a downstream opcode consumes the point.

◉ FlameVM18 · Point

Primitive type

Dict — one structure, three uses.

Map from Int253 keys to arbitrary values.

List

{ 0: a, 1: b, 2: c }

Sequential keys encode without keys on the wire.

Map

{ 42: alice, 99: bob }

Arbitrary keys, total numeric order.

Enum

{ tag: payload }

Single-entry dict encodes a sum-type variant.

Ownership-preserving drill-down

// { 1: { 2: balance } }
1 get  // → outer dict' k=1 inner
2 get  // → inner dict' k=2 balance
mutate
put put     // restore inner, then outer

Tokens are bearer instruments.

◉ FlameVM20 · tokens

Issuance

Two mints, two domains.

Privacy lives where the constraint system lives.

issuepub

runs in an actor frame · internal context

qty Int253 — cleartext
flavor from actor id + tag
push ClearToken
effect IssuePub(qty, flv)

issuepriv

runs in a cell-open frame · external context

qty Variable — Pedersen commitment
flavor from predicate + tag
push Token — range-proven
effect IssuePriv(qC, fC)

Disjoint by construction: transcript separators b"actor" and b"predicate" stop the two domains from colliding on a shared flavor.

◉ FlameVM21 · issuance

Non-fungible tokens

Mix the anchor into the tag.

Anchors are unique per transaction. A tag derived from the anchor yields a flavor no other issuance can share.

// inside an actor method, issuing a unique NFT:
anchor                  // the tx-unique 32-byte anchor
"my-collection-v1"     // domain bytes
append keccak256        // → 32-byte tag
1 issuepub             // qty=1, anchored tag → unique flavor

Verifier reproduces the flavor with issuepubflv / issueprivflv — pure helper, no CS, no effect emitted.

◉ FlameVM22 · NFTs

Confidentiality

An external-context capability.

Pedersen commitments hide quantities and flavors. One Bulletproofs proof at the end attests every constraint accumulated during the script.

External tx reveals

  • The script itself
  • Pedersen commitments
  • Bulletproofs proof
  • Schnorr signatures

External tx hides

  • Unrevealed Taproot leaves
  • Plaintext qty & flavor
  • Variable assignments inside the proof

Internal tx have no native confidentiality — actor state is in the clear. Schnorr ZKPs may still attest facts about secret data.

◉ FlameVM24 · constraints

Custom Sigma-protocols

Schnorr-style ZK from primitives.

Available in both contexts. Building blocks: Point · Int253 · Merlin · MultiscalarMul.

Every verification reduces to "this weighted sum of group elements is the identity". All such checks batch into a single multi-scalar multiplication at finalize, alongside every signature in the transaction.

Architecture

◉ FlameVM26 · concurrency

Resources

Gas  ·  Vbytes.

Gas — compute

Per-block budget split into two pools:

  • Parallel B_par — all external scripts
  • Serial B_ser — all internal allotments

B_par / B_ser ≈ 4 — matches a 4-core verifier. Serial is scarcer; the market prices the difference per byte of fee.

Vbytes — storage

Protocol-defined unit of actor state.

  • 5000 new vbytes per block
  • Each actor pays its size every block
  • Balance hits 0 → frozen, grace period
  • Cleared actors recycle vbytes (100-block maturity)

Both gas and vbytes are committed up front via the external transaction fee. Failure does not refund.

◉ FlameVM27 · resources

Example

Plain account — P2PK

The simplest predicate: a single key, key-path spend.

Locking

// seal tokens under Alice's public key
tokens…  k=1  alice_pk  output

Spending

input                   // materialize cell on stack
signtx                  // Schnorr-bind cell predicate to TxID
// payload tokens are now on the stack
…build outputs, fee, etc.

No script is revealed on chain — cheapest path. Spectator sees only the 32-byte point.

◉ FlameVM28 · plain account

Example

2FA — co-sign, or self-recover with a delay.

Cell predicate is a MuSig of (alice, phone). Co-sign for instant spends; alice can recover solo, behind a 1-week timelock.

Aggregated key path

// predicate: musig(alice_pk, phone_pk)
input  signtx                     // both keys contribute to the aggregated sig

Script path — alice's delayed self-recovery

alice_pk  signtx                  // alice authorizes alone
//   payload tokens are now on the stack

// compute deadline = current tx locktime + 1 week
timelock  drop                    // current locktime (drop unit flag)
604800  add                       // + 1 week (seconds)

// re-lock value under a predicate enforcing:
//   alice_pk signs  ∧  tx.locktime ≥ deadline
alice_pk  recovery_pred           // build the delayed-alice point
1  output                         // value waits 1 week before alice can spend it

The cooling-off window blocks immediate exfiltration if alice's key alone is stolen — the phone (or alice, alerted) has a week to react.

◉ FlameVM29 · 2FA

Example

m-of-n multisig — Taproot reveal.

Each subset of m signers is a leaf in the predicate tree.

input                        // cell on stack
cell ik nbrs pos  script gas bytes args…  k  open
  ↳ alice_pk  signtx
    bob_pk    signtx

The unspent paths stay hidden. Privacy scales with the tree depth, not the number of signers.

◉ FlameVM30 · multisig

Example

Confidential payment — Alice → Bob

Alice spends 250 flames, pays Bob 100, keeps 150 as change. Every quantity flows as a Pedersen commitment.

input  signtx                     // open Alice's cell  →  Token(250, flame)

// Pedersen commitments for the two outputs (qty, flv each)
bob_qC    bob_fC                  // commits to (100, flame) for Bob
chg_qC    chg_fC                  // commits to (150, flame) for change

1  2  mix                          // 1 input  ↔  2 outputs, balanced per flavor
//   stack: Token(bob), Token(chg)

bob_pk    1  output                // → 100 to Bob
alice_pk  1  output                // → 150 change

The Bulletproofs proof at the end attests: inputs balance outputs per flavor, every output qty is 64-bit non-negative. A real tx adds fee — its WideToken debt is absorbed by the same mix.

◉ FlameVM31 · confidential payment

Example

AMM swap — 10 X for some Y.

External tx (user)

input  signtx                // claim X UTXO
10  split                    // split off 10 X
// payload tokens, count k=1
1 refund_pk gas bytes
0 amm_addr
send                         // async message → AMM

Internal tx (AMM recv → swap)

load                         // AMM state dict
// compute Δy = x·Y / (X+x)
// update reserves; mint Y tokens out
… 1 user_pk output        // Y → user
save                         // persist new reserves

If the AMM fails (slippage, depleted reserves), the X tokens bounce as a cell under the user's refund predicate. Gas & vbyte allotments are consumed regardless.

◉ FlameVM32 · AMM

Example

NFT issuance — anchored flavor.

A flavor that no other call can recreate — because no other call shares the anchor.

// inside the collection's actor method:
anchor                       // 32-byte tx-unique value
"my-collection-v1" append
keccak256                    // → unique tag
1  issuepub                  // 1-quantity ClearToken
// → emit IssuePub(qty=1, flv=H(actor_id, tag))

// consumer side: recompute the flavor and check
actor_id  tag  issuepubflv   // → flavor scalar
eq verify

Same pattern with issuepriv + issueprivflv from a cell-open frame — for a confidential NFT under a predicate's identity.
