# ADR 0008 — Taproot-compressed predicate construction

- **Status:** accepted
- **Date:** 2026-05-23
- **Proposers:** Architect (prompted by VM Engineer's port of the Taproot
  predicate construction from `zkvm/src/predicate.rs` into
  `flamevm/src/cell.rs`).
- **Deciders:** Architect
- **Supersedes / related:** ADR 0006 (little-endian everywhere — pins the
  byte order of the `programs.len()` length prefix bound into the
  blinding-key transcript).

## Context

A `Predicate` in Flame is a Ristretto255 point that gates a cell's
spend authority. Flame supports three predicate variants:

- **Key.** A bare Ristretto point. Spending requires a signature under
  the secret key for that point.
- **Program.** A specific bytecode program. Spending requires producing
  the program and executing it under a `signtx` or `verify` boundary.
- **Tree.** A Taproot-compressed predicate
  `P = X + H(X, M)·B`, where `X` is an internal key, `M` is the root
  of a merkle tree of leaf programs, `H(·,·)` is the Taproot tweak
  hash, and `B` is the Ristretto basepoint. Spending follows one of
  two paths:
  - **Key-path.** Sign for `P` directly using the tweaked secret
    `x + H(X, M)` (requires knowing the discrete log of `X`).
  - **Script-path.** Open a leaf program via a merkle proof and the
    `0x93 open` opcode; the verifier checks the program hashes into
    the merkle root, the merkle root combined with `X` reproduces the
    tweak, and the tweaked point equals `P`.

The Tree variant's construction concentrates several consensus-relevant
choices that have, until now, lived only in code (originally
`zkvm/src/predicate.rs`; just ported into `flamevm/src/cell.rs`). Those
choices include the unspendable internal key, the per-program blinding
sibling, the deterministic blinding-key derivation, the four distinct
transcript domains used in the construction, the tree shape, and the
Taproot tweak hash. Each is independently spec-fixed: any change to any
of them produces different `P` for the same `(X, programs)` and is a
hard fork.

The new code also differs from the pre-blinding construction it
replaces — for the same `(internal_key, programs)` pair, the new
construction produces a different `P`. Any opaque predicate point
generated by the old code is no longer satisfiable by the new prover.
The user has explicitly authorized this break, recognizing that no
production state binds to the old construction yet.

This ADR captures the construction as a single canonical reference so
that future audits, re-implementations, and any forward-compatibility
discussion have one place to anchor on rather than re-deriving the
choices from the Rust source.

## Options considered

This ADR pins choices that have already been made in code. The
options below name the alternatives the construction has implicitly
foreclosed; choosing differently in the future would constitute a
hard fork against this ADR.

For the **unspendable internal-key default**:

1. **`B_blinding` (Pedersen secondary generator)** (chosen).
   - Pros: discrete log w.r.t. the primary basepoint is unknown by
     construction (this is the entire purpose of `B_blinding` in the
     Pedersen commitment scheme); the value is already in the
     curve-substrate library; no additional NUMS construction needs
     to be audited or maintained.
   - Cons: ties the NUMS guarantee to the Pedersen-generator hygiene
     of the upstream `bulletproofs` crate.
2. **A bespoke NUMS point derived by hash-to-curve of a fixed string.**
   - Cons: adds a hash-to-curve step that must be implemented,
     audited, and version-pinned. No marginal security gain over the
     Pedersen secondary generator.
3. **A user-mandatory internal key (no `None` option).**
   - Cons: forces every "scripts-only" tree to invent its own NUMS
     point or burn a real key. Strictly worse ergonomics for the
     overwhelmingly common case of "no key-path, just leaves."

For the **per-program blinding-leaf strategy**:

1. **Pair every program with a 32-byte blinding sibling, LSB of
   blinding factor selects program position within the pair** (chosen).
   - Pros: hides on-tree position of any individual program — a
     verifier walking a merkle proof sees the program leaf and one
     opaque neighbor, indistinguishable from any other "program + 32
     opaque bytes" pair; positional indistinguishability is preserved
     against an observer who knows the program but not which slot it
     occupies.
   - Cons: doubles the leaf count (`2 × programs.len()` leaves) and
     adds one transcript-derived 32-byte sibling per program. The
     prover-side cost is small; the verifier sees exactly one extra
     neighbor in the merkle proof.
2. **No blinding leaves; programs occupy positions `0..n`.**
   - Cons: position of a known program is publicly observable from
     the merkle proof. Leaks "which slot is this specific program
     in" information that the blinding construction is designed to
     hide.
3. **Random padding to a fixed power-of-two width with no per-program
   sibling.**
   - Cons: pads only the *count* of leaves, not the *position* of
     any specific program within them. Does not provide
     positional indistinguishability.

For the **blinding-key derivation**:

1. **Deterministic Merlin squeeze bound to
   `(n, blinding_key, programs)`** (chosen).
   - Pros: deterministic from a caller-supplied seed, so the
     prover can regenerate proofs without storing the blinding
     factors; binds all programs so swapping any program rederives
     the entire blinding set; one domain separator per use.
   - Cons: requires the caller to manage the `blinding_key` seed
     (lose it, lose the ability to spend through the tree — though
     the leaves themselves are still derivable from any seed the
     prover chooses, including a fresh one, if the predicate is
     re-derived from scratch).
2. **Per-leaf randomness sampled at proof time.**
   - Cons: non-reproducible; the prover must persist every blinding
     factor alongside the tree.

For the **tree shape**:

1. **Balanced split at `next_power_of_two(n) / 2` at every level**
   (chosen; the zkvm convention).
   - Pros: deterministic and matches the zkvm tree shape so existing
     proof formats and verifier logic carry over unchanged.
   - Cons: proof length for unbalanced trees is suboptimal in some
     edge cases. Not material at the leaf counts predicates
     realistically reach.
2. **Strict binary tree padded to next power of two with sentinel
   leaves.**
   - Cons: adds a sentinel-leaf domain and changes proof length
     uniformly. No benefit over the balanced-split convention for
     the realistic predicate-leaf counts.

## Decision

The Taproot-compressed predicate `Predicate::Tree { internal_key,
programs, blinding_key }` is constructed as follows. Every choice
listed here is **consensus-fixed**: any change is a hard fork.

1. **Tweaked point.** `P = X + H(X, M)·B`, where `B` is the Ristretto
   basepoint, `X` is the internal key, `M` is the merkle root of the
   leaf tree, and `H(·,·)` is the Taproot tweak hash defined in (6).

2. **Internal-key default (NUMS).** When the caller passes
   `internal_key = None`, the construction substitutes
   `PedersenGens::default().B_blinding.compress()` — the secondary
   Pedersen generator whose discrete log w.r.t. `B` is unknown by
   construction. Exposed as
   `pub fn Predicate::unspendable_key() -> CompressedRistretto`.
   This produces a tweaked `P` that nobody can sign for, forcing all
   spends through the merkle tree.

3. **Per-program blinding leaves.** Every program leaf is paired with
   a 32-byte `Blinding` sibling. Within each pair, the program
   occupies position `2k` and the blinding occupies position `2k+1`
   when the LSB of the pair's blinding factor is `0`; positions are
   swapped when the LSB is `1`. The tree therefore has
   `2 × programs.len()` leaves. Observers walking a merkle proof
   cannot distinguish a program leaf from a blinding leaf.

4. **Blinding-key derivation.** Blinding factors are squeezed
   deterministically from a Merlin transcript:
   - Transcript domain: `b"flamevm.taproot.blinding"`.
   - Bound parameters, in order:
     - `b"n"` → `programs.len() as u64`, **little-endian** (ADR 0006).
     - `b"key"` → the caller-supplied 32-byte `blinding_key` seed.
     - For each program in iteration order: `b"prog"` → program bytes.
   - Per program, in order:
     `challenge_bytes(b"blinding", 32)` — that program's blinding
     factor.

5. **Leaf hash domains.** Both leaf variants share the transcript
   domain `b"flamevm.merkle.leaf"` but differ in their content
   label:
   - Program leaf: `append_message(b"program", program_bytes)`.
   - Blinding leaf: `append_message(b"blinding", blinding_32_bytes)`.
   - Both squeeze `challenge_bytes(b"hash", 32)` to produce the
     32-byte leaf hash.

6. **Internal-node hash.** Domain `b"flamevm.merkle.node"`; binds
   `b"left"` → left child hash (32 bytes) and `b"right"` → right
   child hash (32 bytes); squeezes `challenge_bytes(b"hash", 32)`.

7. **Tree shape.** At every level, splits at
   `next_power_of_two(n) / 2`. This is the zkvm convention.

8. **Taproot tweak hash.** Domain `b"flamevm.taproot"`; binds
   `b"key"` → the 32-byte compressed internal key and `b"root"` →
   the 32-byte merkle root; squeezes `challenge_bytes(b"h", 64)`;
   reduces the 64-byte challenge via
   `Scalar::from_bytes_mod_order_wide` to obtain the tweak scalar
   `H(X, M)`.

9. **Wire-format invariance.** The four-string `CallProof` stack
   layout — `(internal_key, neighbors, position, program)` — and the
   `0x93 open` opcode are unchanged from the pre-blinding design.
   Blinding is purely prover-side; verifiers see one additional
   opaque neighbor per program pair but never see the blinding values
   themselves and require no new opcode or stack shape.

10. **Breaking change.** This construction produces different `P` for
    the same `(internal_key, programs)` pair than the previous
    (non-blinding) construction. Any opaque predicate point generated
    by the old code is no longer satisfiable by the new prover. The
    user has explicitly authorized this break for this cycle. No
    forward migration is provided; redeploy any test fixtures that
    embed precomputed predicate points.

## Consequences

- **Positive: single canonical reference.** The four transcript
  domains, the tweak hash, the NUMS default, the blinding-leaf
  strategy, the leaf-pair position rule, and the tree-shape
  convention are now pinned in one document. Future audits and any
  cross-implementation work read this ADR rather than re-deriving
  from `flamevm/src/cell.rs`.
- **Positive: positional indistinguishability.** A verifier walking a
  merkle proof cannot identify which leaf in the tree corresponds to
  any specific program; every leaf looks like a program leaf paired
  with an opaque sibling.
- **Positive: deterministic, NUMS-by-construction key-path
  unspendability.** Scripts-only trees do not require any per-protocol
  hash-to-curve infrastructure; the NUMS point reuses the Pedersen
  secondary generator that the curve substrate already maintains.
- **Positive: little-endian everywhere holds.** The single
  fixed-width integer bound into the blinding-key transcript
  (`programs.len() as u64`) is LE, consistent with ADR 0006.
- **Negative: any transcript-label or domain-separator rename is a
  hard fork.** The four domain strings
  (`b"flamevm.taproot.blinding"`, `b"flamevm.merkle.leaf"`,
  `b"flamevm.merkle.node"`, `b"flamevm.taproot"`) and every
  bound message label (`b"n"`, `b"key"`, `b"prog"`, `b"blinding"`,
  `b"program"`, `b"hash"`, `b"left"`, `b"right"`, `b"h"`) are now
  consensus-relevant strings. Renaming any one of them produces
  different predicate points for the same inputs.
- **Negative: tree shape diverges from a strict-power-of-two padded
  tree.** Acceptable — matches the zkvm convention and the existing
  CallProof shape.
- **Negative: this ADR ratifies a one-cycle break in
  predicate-point stability.** Any external system that had
  precomputed predicate points against the prior construction is
  invalidated. The user has explicitly authorized this.
- **Follow-up work required:**
  - **Recommended for immediate follow-up (one-liner):**
    `PredicateTree::scripts_only(programs, blinding_key)` — a thin
    convenience wrapper for `new(None, programs, blinding_key)`. It
    introduces no new consensus surface; it only saves callers from
    having to thread the explicit `None`. Worth porting now.
  - **Deferred (small public-API addition, but key-path spending is
    not in scope for the near term):**
    `PredicateTree::adjustment_factor() -> Scalar` and its companions
    `outer_key()` / `inner_predicate()`. These are needed for
    key-path spending so the prover can compute the tweaked signing
    scalar `x + H(X, M)`. Without them, FlameVM has no ergonomic way
    for a prover to sign for a Tree-variant predicate via the
    key-path. Key-path spending is mathematically supported by the
    construction in this ADR but not exposed through the API. The
    near-term predicate use case is script-path-only, so this
    helper is deferred. **`[[adr-future-key-path-spending]]`** — a
    future ADR will reopen this once a concrete site demands
    key-path spending (e.g., MuSig-aggregated internal keys for
    Tree-variant cells).
- **Affected artifacts:** `design.md` §Cells and actors (cross-reference
  added); `flamevm/src/cell.rs` (already implements the
  construction, no edit by Architect); future
  `flamevm/spec.md` §Predicates / Taproot section (VM Engineer to
  author, referencing this ADR as the consensus-fixed source).

  `P = X + H(X, M)·B`; Flame's variant differs in the tweak hash
  construction (Merlin transcript with Flame-specific domains, not
  tagged SHA-256), the curve (Ristretto255, not secp256k1), and the
  leaf-blinding strategy (per-program blinding sibling, not raw
  script leaves).
